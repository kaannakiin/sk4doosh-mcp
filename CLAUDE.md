# sk-mcp

"Swagger for Agents": an MCP layer embedded into existing backends — spec + SDK per language.

## Package Boundaries

`products/` is a separate product line that shares only the toolchain (`@sk-mcp/eslint-config`, `@sk-mcp/typescript-config`). Filter by scope, not by directory: `--filter='@chat/*'` and `--filter='!@chat/*'` partition the repo.

## Immutable Rules

- **Single source of truth**: Never manually define TS/C# types for spec concepts (`EndpointDescriptor`, `ToolDefinition`, `Fixture`, `Auth`, etc.). Change the schema → run `pnpm turbo run gen` → use the generated types. Never manually modify files under `packages/core/src/generated/` or `sdks/dotnet/src/SkMcp.AspNetCore/Generated/`; they are committed to the repository.

- `packages/core/src/index.ts` may only re-export `export type` from the canonical files. Never re-export the embedded `EndpointDescriptor`/`ToolDefinition` copies from `generated/fixture.ts` (single-definition rule).

- In schemas, `$id` ≡ the file name. The following 2020-12 keywords must not be used: `prefixItems`, `unevaluatedProperties`, `$dynamicRef`, `dependentSchemas` (the code generator does not support them).

- If a schema change breaks fixtures, update the fixtures in the same change.

- **Comments**: No `//` line comments, no TODOs, no progress notes, no JSON comments — explanations go in the spec prose or documentation. Two exceptions, both `/** */` JSDoc/TSDoc:

  1. **Contract** on exported functions, classes, types and interfaces: purpose, `@param`, `@returns`. Factual only. A well-named item needs none.
  2. **Guard**, anywhere it is needed: a comment may state WHY when it protects an invariant, a security property, or a measured trap. It names what the guard is and what breaks without it, and may cite the decision, measurement or test that pins it. Precedents: [limits.ts](packages/xml-mcp/src/limits.ts) (`W >= 2S-1`), [doctype.ts](packages/xml-mcp/src/doctype.ts) (the refused encoding families), [text.ts](packages/xml-mcp/src/text.ts) (the Turkish dotted I), [listing.ts](packages/file-core/src/listing.ts) (RegExp backtracking).

  Design narration is still forbidden: no restating the code, no explaining what a tier "is for", no history.

- The two product lines do not cross. No `apps/*`, `packages/*` or `sdks/*` package may depend on `@chat/*` (`boundaries.tags.chat.dependents.allow: ["chat"]` in `turbo.json`, checked by `pnpm boundaries`), and `@chat/*` source may not import `@sk-mcp/*` product packages (`@sk-mcp/eslint-config/chat`). The concrete trap: `@sk-mcp/sdk-nestjs` is on **zod 3** and `@chat/contracts` is on **zod 4**; two zod majors in one process make `instanceof ZodError` and schema identity fail silently.

- Every zod schema in the chat product lives in `products/chat/contracts`. A `z.` call inside `products/chat/api/src` or `products/chat/web/src` is a defect, environment schemas included (`config/api-env`, `config/web-env`): a schema declared next to one consumer drifts from the other side of the wire within a release. Type-only `zod` imports stay legal so a pipe can name `ZodType`. Enforced by `@sk-mcp/eslint-config/chat`'s `chatApp` export.

- `@chat/contracts` has no barrel and no bare import. One topic per file under a domain folder (`common/`, `chat/`, `http/`, `config/`), schema and its `z.infer` type in the same file, next to the dependency-free pure functions over that vocabulary (`isLocale`, `negotiateLocale`) so the two sides can never negotiate a locale by two different algorithms. Consumers name the leaf: `@chat/contracts/chat/send-message`, never `@chat/contracts`. The `exports` map has no `"."` entry, so the bare specifier fails at runtime as well as in lint. Adding an `index.ts` would put every domain in `@chat/api`'s module graph, which it pays for unbundled.

- `@chat/api` and `@chat/web` resolve `@chat/contracts` through `exports.default → ./dist/index.js`. Run them through Turbo (`pnpm dev:chat`, `pnpm turbo run test --filter=@chat/api`), never `pnpm --filter @chat/api <task>`: the bare filter skips `dependsOn: ["^build"]` and runs against a stale `contracts/dist`.

- **Language**: `docs/` (internal design records and ADRs) is in Turkish. `packages/spec/` and `apps/docs/` are in English — the spec is the documentation site's normative source and has to be readable by the same audience. Everything machine-readable (JSON fields, tool names, code identifiers) is in English everywhere. In `products/chat`, identifiers, JSON fields and i18n **keys** are English too; user-facing copy lives only in `src/i18n/locales/<locale>/*.json` — a UI string literal in a component under `products/chat/web/src` is a defect.

- Always build core through Turbo (`pnpm turbo run build`) — `pnpm --filter @sk-mcp/core run build` skips generation and risks using stale types.

- Silent conflict resolution in tool naming is forbidden: a conflict is an error ([packages/spec/naming.md](packages/spec/naming.md)).

- `packages/file-core` carries **no format-specific vocabulary**. User-facing nouns arrive through the injected `Vocabulary`; error instances arrive through the injected `ErrorFactory`. A string literal saying "workbook", "sheet", "spreadsheet" or "excel" inside `packages/file-core/src` is a defect.

- A published package may never depend on a `private: true` workspace package. `pnpm publish` silently rewrites `workspace:^` to the private package's `0.0.0`, the publish succeeds, and the failure surfaces in the consumer's `install`. The CI `pack` job guards this ([.github/scripts/check-npm-tarballs.py](.github/scripts/check-npm-tarballs.py)).

- No file-server tool response may bypass the payload budget. `json()` and `toToolError()` in `packages/file-core` are the only sanctioned response constructors; a hand-built `CallToolResult` in a product package is a defect.

- Visibility ≠ enforcement: search filtering is not a security mechanism; enforcement must always happen in the backend pipeline at invoke time.

## Commands

- `pnpm build` / `pnpm lint` (includes validation) / `pnpm check-types` / `pnpm validate`

- TS tests: `pnpm turbo run test --filter=@sk-mcp/core` / `--filter=@sk-mcp/file-core` / `--filter=@sk-mcp/excel-mcp` / `--filter=@sk-mcp/xml-mcp` / `--filter=@sk-mcp/sdk-nestjs` (Vitest). Run them **through Turbo**, not `pnpm --filter <pkg> test`: that form skips `dependsOn: ["^build"]`, and `excel-mcp` resolves `@sk-mcp/file-core` through `exports.default → ./dist/index.js`, so a bare filter can test against a stale `dist`.

- dotnet side: `pnpm turbo run build --filter=@sk-mcp/sdk-dotnet` (the shim invokes `dotnet build`)

- DemoApi: `dotnet run` — located in `sdks/dotnet/samples/DemoApi`, listens on `http://127.0.0.1:5178`; MCP endpoint `/mcp` (requires a bearer token); demo shortcut `POST /auth/token {"user":"alice"|"bob"|"carol"}`; full OAuth 2.1 flow via the in-repo `samples/DemoAuthServer` mounted at `/oauth` (PRM at `/.well-known/oauth-protected-resource/mcp`)

- agent-client (MCP acceptance harness, drives both the dotnet and the Nest demo): `node sdks/nestjs/samples/agent-client/dist/main.js --scenario smoke|validation-retry|error-envelope`; `SKMCP_AUTH=oauth|token|bearer` (`bearer` reads `SKMCP_TOKEN`, for a real backend), `SKMCP_USER`, `SKMCP_BASE_URL`

- Nest demo: located in `sdks/nestjs/samples/demo-api`; run with `node dist/main.js` (first run `pnpm turbo run build --filter=@sk-mcp/demo-nestjs`); same `/mcp` + `/auth/token` contract

- Docs site: located in `apps/docs` (TanStack Start + Mantine + Tailwind); run with `pnpm --filter @sk-mcp/docs dev`, listens on `http://localhost:5180`; pages are markdown under `src/content/*.md`. This site is sk-mcp's public face, so its content and UI strings are written in **English**, as is `packages/spec`, which the site links to as its normative source; the Turkish-prose rule applies to `docs/` only. `apps/docs` carries no i18n layer by design — that decision is scoped to `apps/docs` and does not extend to `products/`.

- Chat product: `pnpm dev:chat` (`turbo run dev dev:types --filter='@chat/*'`) runs `@chat/contracts` in watch mode, `@chat/api` on `http://127.0.0.1:5191` and `@chat/web` on `http://localhost:5190`; `pnpm dev:sk` is the complement. `@chat/api` needs **both** task names: `dev` runs `node --watch dist/main.js` after its own `build` (its `dev` depends on `build`, not only on `^build` — otherwise a clean checkout starts a runner with no `dist`), and `dev:types` is the `tsc --watch` that keeps emitting into it. Turbo supervises both, so neither is backgrounded with `&`. Env comes from `products/chat/{api,web}/.env` through `@nestjs/config` and Vite — Turbo runs in strict env mode and does not load `.env` files itself, so anything passed on the command line has to be declared in that package's `turbo.json` (`env` for build-time values, `passThroughEnv` for runtime ones).

- Package boundary check: `pnpm boundaries` (`turbo boundaries`, experimental — not part of `pnpm lint`).
