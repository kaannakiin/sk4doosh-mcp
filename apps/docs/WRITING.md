# Writing the docs

Every page under `apps/docs` follows these rules. The basis is **Diátaxis**, Daniele Procida's
taxonomy (Django, Kubernetes, Cloudflare and Canonical use the same one).

This file is for the people writing the site; it is not published on it.

## Four modes

Diátaxis splits documentation along two axes: practical or theoretical, learning or working.

|               | Learning                         | Working                       |
| ------------- | -------------------------------- | ----------------------------- |
| **Practical** | **Tutorial** — takes you by hand | **How-to** — solves one task  |
| **Theory**    | **Explanation** — why it is so   | **Reference** — what there is |

The directory tree carries **two axes**: product line × mode. The first segment is the product, the
second is the Diátaxis bucket — a page's bucket is the folder directly under its product folder:

```text
src/content/
  products.json               <- product registry: id, label, tagline (array order = display order)
  http-catalog/
    00-introduction.md        <- unbucketed: the product's orientation page, one page, short
    tutorial/
    how-to/
    reference/
    explanation/
  excel-mcp/                  <- later: the same structure, its own buckets
```

Order comes from the number in the file name, the title from the first `#` line, and the slug from
the file name with the number prefix removed. The route is `/docs/<product>/<slug>`, so a slug only
has to be unique **within its product**; two products may both have an `introduction`. Renumbering
never changes a slug — inserting a page breaks no URL.

The sidebar is generated by `src/lib/content.ts`. A new **page** is registered nowhere. A new
**product** is registered in one place, `src/content/products.json`: create the folder, add one
entry. `pnpm --filter @sk-mcp/docs validate` fails CI on every structural violation.

## Rules

These are not "nice to have". Documentation rots when they are broken.

### 1. One page, one mode

The most broken rule. A reference table in the middle of a tutorial breaks both modes: the learner
drowns in the table, and the person working has to skip the narrative around it.

The same topic can be told four times on four pages, and should be. That is not repetition; those
are the answers the same topic gives to different questions. The four visibility pages are the
example.

### 1b. One page, one product line

A page covers one product line; its path says which. A request for a page comparing two of our
products is really two explanation pages — or none. What the products share is the spec, not a
product, and shared narrative belongs in `packages/http/spec/`.

A product folder is named after the product's package or directory (`excel-mcp`, `xml-mcp`,
`file-core`). `http-catalog` is the deliberate exception: it names a capability spread over two
SDKs — the ASP.NET Core and NestJS HTTP endpoint catalog — rather than a package.

### 2. Reference is generated, not written

Nothing that has a machine-readable source is written by hand. `packages/http/spec/schemas/*.schema.json`
is this repository's single source of truth; the rule that holds for type generation holds for
documentation too.

A schema field copied by hand into a reference page is a lie within three months. Even where no
generation pipeline exists yet, the page **links to the schema** and does not copy its field list.

### 3. RFC 2119 keywords only in the spec

`MUST` / `SHOULD` / `MAY` appear only in `packages/http/spec/*.md`. Normative language in a
tutorial breaks both: a tutorial uses the imperative because it teaches, the spec uses normative
language because it binds implementers. They cannot share words.

Site pages link to the spec; they do not restate it.

### 4. Every code example runs

An example comes from a real test file, from a conformance fixture, or from a command someone ran.
An invented example is a lie within three months, and it spends the reader's trust in one go.

If an example that has not been run is published anyway, the page says so at the top. It is never
published silently.

Output blocks holding sample data are **never translated or edited by hand**. If the sample's own
string is in the wrong language, fix the sample and regenerate the output, or disclose it on the
page. This is not hypothetical: a measured JSON block in `reference/02-schema-conversion.md`
carried Turkish `description` values for months, and the rule as it then stood did not catch it.

### 5. One path in a tutorial

"Alternatively", "if you prefer", "depending on your preference" are forbidden. Branching is the
how-to's job. A tutorial's contract is: follow the steps in order and end up with something that
works. Every branch weakens that contract.

A tutorial goes to the end; success is a visible result, not "you are now ready".

### 6. Policy names do not leak

`packages/http/spec/visibility.md` invariant 3: policy names never reach the agent. The same holds
for the docs — examples use no real customer policy name, tenant name or endpoint path. DemoApi's
cast of `OrdersRead`, `BusinessHours` and `alice`/`bob`/`carol` exists for this.

### 7. Rationale lives next to what it constrains

There is no separate decision-record tree. A normative rule is in the spec, a measurement or an
invariant is in a guard comment, a package-level decision is in that package's README. A site page
may explain that rationale but must not be its only source: the answer to "why did we do it this
way?" is versioned with the code.

## Titles

The mode is readable from the title:

| Mode        | Pattern                    | Example                                 |
| ----------- | -------------------------- | --------------------------------------- |
| Tutorial    | `<Verb>ing your first <X>` | `Seeing visibility filtering in action` |
| How-to      | `How to <verb>`            | `How to control what a caller can see`  |
| Reference   | A noun phrase              | `Visibility decision`                   |
| Explanation | A question or a claim      | `Why visibility is not enforcement`     |

A title that asks a question is an explanation. One that starts with a verb is a tutorial or a
how-to. A noun is reference. If you do not know which bucket a title belongs to while writing it,
you are not ready to write the page.

## Language

- Site content and UI strings are **English** — the site is sk-mcp's public face.
- `packages/http/spec/` is **English** — the site links to it as normative, and the same audience
  has to read it.
- There is no i18n layer, on purpose: one language, no drift.

The **Google developer documentation style guide** is the reference for prose. [Vale](https://vale.sh)
could enforce it; it is not wired up today and is left to human review.

## Checklist for a new page

0. Which product line? Is the file under `src/content/<product>/`, and is the product registered in
   `products.json`?
1. Which bucket? If you cannot answer, do not write the page.
2. Is the file in the right folder, and does its number prefix give the right order?
3. Does the title follow the mode's pattern?
4. Did every code example run? If not, does the page say so?
5. Is there a field list copied from a schema? Turn it into a link.
6. Has a section doing another mode's job slipped in? If so, that section is a new page.
7. Is the slug unique within this product line, and does every internal link point at a page that
   exists?
